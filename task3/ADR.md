### <a name="_qmphm5d6rvi3"></a>**Решение**

Основной проблемой текущей системы является перегруженная АБС, которая служит единой точкой отказа и узким местом производительности. Прямое взаимодействие с ней из Интернет-банка или с Сайта приведёт к нестабильности всей системы банка.

**Логика принятия решений:**
1. **Защита АБС:** Вводится Промежуточный Интеграционный Слой (Middleware), который будет принимать все запросы от фронтальных систем и асинхронно передавать их в АБС через очереди.
2. **Асинхронность:** Для операций, не требующих немедленного ответа (подача заявки, импорт ставок), используется Kafka. Для текущей версии Интернет-банк, несовместимой с Kafka, создаётся Адаптер протоколов внутри шлюза.
3. **Производительность и кэширование:** Внедряется кэш на уровне шлюза и микросервисов для обеспечения быстрых откликов.
4. **Микросервисы как пилот:** Логика разбивается на три основных микросервиса (Сервис Заявок, Сервис Управления Ставками, Сервис Нотификаций).
5. **Технологический стек:** Используется MS SQL для хранения данных новых сервисов и Java/.NET Core для разработки.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. **Прямая синхронная интеграция Интернет-банка и АБС (REST/SOAP)**
   - Отклонена из-за: Требования R4 и P4. Это создало бы колоссальную нагрузку на БД АБС при наплыве клиентов.

2. **Использование только Oracle для новых сервисов**
   - Отклонена из-за: Требования S1 и S2, а также внутренней экспертизы. В банке уже есть сильная команда по MS SQL.

3. **Очереди на базе RabbitMQ вместо Kafka**
   - Отклонена из-за: Требования S3. Kafka является корпоративным стандартом на перспективу.

**Недостатки, ограничения, риски**

1. **Сложность внедрения (Риск):** Ручная обработка заявок на этапе MVP и необходимость синхронизации между новой системой и устаревшей АБС.
   - *Митигация:* Разработать детальные механизмы Saga для обеспечения согласованности данных.

2. **Несовместимость Интернет-банк и Kafka (Ограничение):** Текущая версия платформы Интернет-банка не может работать с Kafka напрямую.
   - *Митигация:* Разработать Адаптер протоколов, который будет принимать синхронные REST-запросы и класть их в очередь.

3. **Нагрузка на адаптер:** "Толстый" адаптер может стать узким местом.
   - *Митигация:* Сделать адаптер максимально легковесным, обеспечив его горизонтальное масштабирование.

4. **Миграция XLS-данных:** Переход от ручного ведения XLS к централизованной БД может встретить сопротивление.
   - *Митигация:* Сохранить интерфейс импорта из XLS для бесшовного перехода.

5. **Задержки при асинхронной обработке:** Клиент может не получить мгновенное подтверждение.
   - *Митигация:* Предусмотреть выдачу мгновенного статуса "Заявка принята в обработку" и отправлять уведомления при смене статуса.

6. **Производительность кэша:** Неправильная политика инвалидации кэша может привести к отображению устаревших ставок.
   - *Митигация:* При импорте новых ставок сразу сбрасывать кэш. Использовать TTL для кэша в пределах нескольких минут.
