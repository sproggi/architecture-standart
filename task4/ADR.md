### <a name="_b7urdng99y53"></a>**Название задачи: Обеспечение колл-центров (внутреннего и партнерского) актуальными депозитными ставками для консультирования клиентов** 
### <a name="_hjk0fkfyohdk"></a>**Автор: Alexey Sprygin**
### <a name="_uanumrh8zrui"></a>**Дата: 28.07.2026**
### <a name="_uanumrh8zruu"></a>**Контекст**
В рамках MVP по цифровизации депозитов выявлен риск перегрузки колл-центра из-за возрастной аудитории и маркетинговой кампании. Необходимо дать доступ к ставкам внутреннему колл-центру (с высокими требованиями к скорости) и внешнему партнерскому колл-центру (работает через файловый обмен).

---

### <a name="_3bfxc9a45514"></a>**Функциональные требования**

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :--- | :--- | :--- | :--- |
| **UC-07** | **Менеджер внутреннего Кол-центра**, **Система Кол-центра** | Просмотр актуальных ставок в реальном времени | 1. Менеджер открывает свой рабочий интерфейс.<br>2. Система кол-центра обращается к **API Сервиса ставок** (микросервис) для получения актуальных данных.<br>3. Менеджер видит ставки и может консультировать клиента без задержек. |
| **UC-08** | **Администратор**, **Партнерский кол-центр (внешняя система)** | Экспорт ставок для партнера (SFTP/Файлы) | 1. Система банка (по расписанию или вручную) формирует XLS-файл с актуальными ставками.<br>2. Файл помещается во внешнюю файловую шару или SFTP-каталог, доступный партнеру.<br>3. Партнер забирает файл и загружает его в свою систему для консультантов. |
| **UC-09** | **Микросервис ставок**, **Кэш (Redis)** | Кэширование ставок для быстрых ответов | 1. При запросе ставок из Кол-центра сервис проверяет кэш.<br>2. Если данные актуальны — отдает из кэша (время ответа < 100 мс).<br>3. При изменении ставок (UC-05) кэш сбрасывается автоматически. |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования (дополнения к существующим)**

| **№** | **Требование** | **Обоснование** |
| :--- | :--- | :--- |
| **R4** | Время ответа для внутреннего кол-центра должно быть менее **300 мс** (пиковая нагрузка — 500 RPS). | Пожилые клиенты не терпят ожидания на линии, это влияет на NPS. |
| **R5** | Внешний партнерский кол-центр должен получать файлы не реже 1 раза в 15 минут в период маркетинговых кампаний. | Ставки могут меняться динамически, необходимо информировать партнеров оперативно. |
| **S3** | Передача файлов партнеру должна осуществляться по защищенному протоколу (SFTP/FTPS) с аутентификацией по ключам. | Исключение утечек коммерческой информации. |
| **T6** | Сервис ставок должен быть выделен в отдельный **микросервис** (как пилот) для независимого масштабирования. | Это позволит горизонтально масштабировать только зону ответственности колл-центра. |

---

### <a name="_qmphm5d6rvi3"></a>**Решение**

Мы расширяем ранее спроектированный Промежуточный слой (Middleware) и Сервис Управления Ставками, добавляя две новые точки входа:

1. **REST API для внутреннего Кол-центра:** Внутренняя система кол-центра (CRM) подключается к новому эндпоинту микросервиса `Rate Service`. Данные отдаются из кэша (Redis) для максимальной производительности.

2. **Файловый экспорт для Партнера (SFTP):** Создается отдельный **Адаптер экспорта** (в составе того же микросервиса или отдельного воркера), который по расписанию:
   - Выгружает текущие ставки из основной БД (MS SQL) и кэша.
   - Формирует плоский файл (например, CSV с разделителями).
   - Кладет файл в выделенный каталог для внешнего SFTP-сервера.

3. **Синхронизация с АБС:** Так как ставки занозятся через UC-05 (импорт XLS), при сохранении новых ставок мы триггерим событие в Kafka (`RateChangedEvent`). Это событие подхватывают:
   - Микросервис **API** (чтобы обновить REST-кэш).
   - **Воркер экспорта** (чтобы понять, что пора генерировать новый файл для партнера).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| **Альтернатива** | **Причина отклонения** |
| :--- | :--- |
| **Прямой доступ партнера к БД банка (VPN + SQL)** | Отклонено из-за требований безопасности (S1, S2). Предоставление внешнему контрагенту доступа к нашим реляционным данным несет огромные риски утечек и нарушения целостности. |
| **Передача ставок голосом или через личные кабинеты партнеров** | Отклонено из-за высокой операционной нагрузки (OpEx). Это потребовало бы ручного труда каждого менеджера бэк-офиса для ежедневной рассылки, что противоречит цифровизации. |
| **Использование SOAP-сервиса для партнера (вместо файлов)** | Отклонено из-за прямого требования партнера (нет API-возможностей). Партнер готов работать только с файлами. |
| **Сборка файла экспорта на лету (при каждом запросе партнера)** | Отклонено из-за рисков генерации тяжелых файлов (если ставок много) и нестабильности SFTP-соединения. Лучше генерировать заранее. |

### <a name="_bjrr7vnph80c"></a> **Недостатки, ограничения и риски нового решения**

| **Риск / Ограничение** | **Митигация** |
| :--- | :--- |
| **Рассинхрон данных:** Партнерский кол-центр может работать со вчерашними ставками, если файл не обновился. | Внедрить механизм TTL и версионирование файлов. В каждом файле указывать дату/время публикации. Оптимальный интервал генерации: **каждые 10-15 минут**. |
| **Нагрузка на БД:** Постоянное чтение ставок для файлов и API создаст дополнительную нагрузку. | **Решение:** API и Генератор файлов используют **только кэш (Redis)**. В БД ходим только при импорте нового XLS (редкая операция). |
| **SFTP падение:** Если внешний SFTP-сервер партнера недоступен, мы не можем отправить файл. | Воркер должен иметь очередь повторных попыток (Retry с backoff) и алерты в мониторинг (Zabbix/Prometheus). |
| **Сложность поддержки двух протоколов (REST + SFTP).** | Это стандартная практика интеграции. Логика формирования данных выносится в общий слой (`Domain Model`), а адаптеры (REST и SFTP) — это просто разные "обертки" вокруг одной бизнес-логики. |
| **Несовместимость Интернет-банка и Kafka (существующее ограничение)** | Сохраняется Адаптер протоколов из первоначального ADR. Для колл-центра это не актуально, так как они работают через REST напрямую. |

### <a name="_bjrr7vnph80c"></a> **Список крупных задач для дорожной карты (Планирование)**

Чтобы реализовать эти изменения, необходимо разбить работу на этапы для разных команд (команда Middleware, команда Кол-центра, команда Инфраструктуры, Команда по работе с партнерами).

| **№** | **Приоритет** | **Система / Команда** | **Задача (Epic / Feature)** | **Описание** |
| :---: | :---: | :--- | :--- | :--- |
| **1** | Высокий | **Команда Микросервисов** | Разработка API для ставок | Реализовать REST-эндпоинт `/api/v1/rates/current` в новом микросервисе. Подключить кэширование (Redis). |
| **2** | Высокий | **Команда Интеграции (Middleware)** | Подписка на события изменения ставок | Настроить продюсера Kafka (или существующий) для отправки события `RateChangedEvent` при импорте XLS (UC-05). |
| **3** | Высокий | **Команда Микросервисов** | Разработка Воркера-Экспортера | Создать сервис, который слушает события Kafka (или работает по расписанию), генерирует CSV/XLS и кладет во внутренний каталог. |
| **4** | Высокий | **Команда Инфраструктуры** | Настройка SFTP-сервера / DMZ | Организовать защищенную зону (DMZ) для внешнего SFTP-доступа партнера. Настроить пользователей и ключи шифрования. |
| **5** | Средний | **Команда Кол-центра** | Адаптация CRM-системы | Переключить интерфейс менеджеров с вызова старого монолитного API на вызов нового REST-сервиса банка. Убрать ручные таблицы. |
| **6** | Средний | **DevOps / SRE** | Настройка мониторинга и алертов | Добавить метрики для отслеживания времени генерации файлов, успешности отправки по SFTP, и времени ответа API (< 300 мс). Настроить дашборды в Grafana. |
| **7** | Средний | **Команда внешнего Партнера** | Настройка авто-загрузки файлов | Разработать на стороне партнера скрипт для автоматического забора файла с SFTP и загрузки в их внутреннюю базу знаний. |
| **8** | Низкий | **Аналитики / Бизнес** | Тестирование сценария для пожилых | Провести UX-тестирование новой цепочки: клиент звонит в кол-центр (внутренний или партнерский) -> консультант видит актуальную ставку за 1 секунду. |
